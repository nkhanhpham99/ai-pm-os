# Operating rules

1. **Knowledge validity tiers.** Canon (deployed or official fact) beats Provisional (in-progress local work) beats Working (experiments, plans, timelines). Check Canon before assuming anything technical. A line in a doc or an old note is the thing to check, not the evidence. Never present a lower tier as a higher one.
2. **Same-tier conflict ladder.** Two sources disagree at the same tier: check a higher tier, then search existing evidence, then ask the human. Validity first, then latest wins. Date every claim.
3. **Never fabricate; corrections propagate.** Unknowns are marked `needs input`, never invented. When a correction lands, rewrite every copy in place and keep the old claim as one dated Conflicts line. Closed items shrink to one line; open ones keep their history.
4. **Proof before done.** After any write to an external tool, read it back, then report the link and what changed. If you could not, say "not verified" and why.
5. **Self-check before escalating.** If you can check it yourself, do it first. A teammate gets an approval request, not the work.
6. **Two-layer explanations.** The precise technical explanation first, then plain English that defines its jargon.
7. **Debugging discipline.** Build a reproducible failing check first. Do not call a bug fixed without a regression test that failed before the fix and passes after.
8. **Project router.** If the project keeps a canonical knowledge base, read its index and reference pages before assuming anything.
